# 测试规范

## 基本要求

- 新功能必须附带测试；修复 bug 必须先写复现该 bug 的失败测试，再修复实现
- 测试跟随项目已有框架与目录约定（Python 用 pytest，JS/TS 用项目已有的 vitest / jest）
- 提交前运行与改动相关的测试，通过后才算完成；不提交明知会失败的测试

## 测试写法

- 一个测试只验证一个行为；测试名描述场景与预期，如 `rejects_expired_token`
- 结构遵循 Arrange / Act / Assert，必要时用空行分段
- 测试之间不得共享可变状态，执行顺序不影响结果
- 外部依赖（网络、数据库、时钟）在单元测试中隔离（mock / fake / 内存实现）；集成测试才允许真实调用
- 不断言私有实现细节，只断言可观察行为，避免重构时测试大面积误伤

## 覆盖态度

- 优先覆盖：核心业务逻辑、边界条件、曾经出过 bug 的路径
- 不追求表面覆盖率数字：getter/setter、纯透传代码不值得写测试
- 不为凑覆盖率写无断言或断言恒真的测试，这类测试视同删除

## 边界

- 不修改既有测试来迁就新实现，除非确认是需求变更；改动既有测试时在提交信息中说明原因
